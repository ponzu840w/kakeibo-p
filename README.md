# kakeibo-p

個人の全金融口座の残高(ストック)と取引(フロー)を一元把握する、
ファイルベースの家計管理システム。DBMSなし・webUIは基本的に静的HTML。

めちゃくちゃclaude製。

## 設計原則

1. **raw/ は不変の一次資料**。ダウンロードした明細CSV等の原本は改変しない。（ファイル名にユニーク性がないものに関して最初に一回リネームをすることはあり）
2. **raw/ 以外はすべて派生物**。`ledger/` も `site/data.js` も `build.py` の再実行で raw/ から再生成可能。パーサ修正後に全履歴を作り直せる設計とする。
3. **決定論的データ処理・分析と、非決定論的分析を峻別する**。取込・正規化・分類・集計は決定論的に実行。
4. **DBMSは使わない**。ソース・オブ・トゥルースはテキストファイル (JSONL/TOML/CSV)。
5. webUIは `site/index.html` をダブルクリックで開ける静的構成を基本とする。データは `data.js` に埋め込む(file:// で fetch が CORS死するため)。外部CDN依存なし、チャートは素のSVG。

## リポジトリ構成

```
kakeibo-p/                # gitリポジトリ(コードのみ)
├── build.py              # パイプライン本体(重複排除・分類・突合・集計・出力)
├── parsers.py            # ソース別パーサと形式判別(新ソース追加はここだけ)
├── model.py              # 基本部品(正規化・Txn型・パス定数)
├── serve.py              # UIローカル配信+上書き保存API(任意。file://でも動く)
├── site/                 # 静的UI(index.html / style.css / js/ に機能別分割)
│   ├── data.js            # 集計用データ(派生物・git外・ローカル)
│   └── data.demo.js       # デモ用データ(実データがない時のフォールバック)
├── tests/                 # パーサのサンプルベーステスト(架空データ)
├── demo/build_demo.py    # 架空データの生成とデモビルド
├── parsers_extra.py      # ローカル拡張パーサ(任意。勤務先関連などを分離)
├── tests_extra/          # ローカル拡張のテスト(任意。discoverに合流)
├── ledger/YYYY-MM.jsonl   # 正規化済みトランザクション(派生物・git外・ローカル)
├── CLAUDE.md → data/CLAUDE.md   # リンク(git外)
└── data/                  # 個人データの実体。git外
    ├── raw/<source>/      #   明細の原本(不変。配置・命名は自由)
    ├── inbox/             #   取込の投入口(buildが raw/ へ自動振り分け)
    ├── accounts.toml      #   口座台帳(howto=取得手順メモ含む)
    ├── rules.toml         #   分類ルール(正規表現→カテゴリ)・振替定義・中分類
    ├── overrides.toml     #   レコード単位の手動上書き(UI生成物)
    ├── uistate.toml       #   鮮度モニタの状態(UI生成物)
    └── build_log.jsonl    #   ビルド実行の追記専用ログ(build.py が書く。
                           #    再生成不能な履歴なので派生物でなく状態ファイル。
                           #    UIヘッダの「ログ」から直近分を閲覧できる)
```

**個人データはgitに入れない。** `data/` の実体をクラウドストレージ
(OneDrive等)に置き、シンボリックリンクにすれば build.py はそのまま動く。
派生物(ledger/, site/data.js)は再生成可能なのでローカルに置くだけでよい。

## 使い方

```sh
python3 build.py          # 全再生成(ledger/ と site/data.js を書き直す)
python3 build.py --check  # 生成せず取込サマリ・検証・鮮度警告のみ表示
python3 serve.py          # UIをローカル配信(明細の上書き編集はこちらでのみ可能)
python3 serve.py --demo   # 架空データで配信(data/ が無くても動く。再ビルドも可)
python3 -m unittest discover tests   # テスト
python3 demo/build_demo.py           # 架空データを生成してデモビルド
```

Python 3.11+(標準ライブラリのみ)。

まず動きを見たいだけなら `demo/build_demo.py` を実行して(または同梱の
`site/data.demo.js` のまま)`site/index.html` を開けば、固定シードで生成した
架空の2年分の家計でダッシュボード一式が動く。実データ(`site/data.js`)を
ビルドするとそちらが優先される。

`python3 serve.py --demo` なら読み書きが丸ごと `demo/` に向くので、上書き編集・
取込・再ビルド(↻)まで架空データのまま試せる。`data/`(個人データ)が無い
状態で `build.py` や `serve.py` をそのまま実行するとエラーで止まる。

## 実装済みパーサ

ファイル名でなく内容(ヘッダ)でソースを自動判別する。ソース固有の仕様・罠は
parsers.py の各パーサの docstring を参照。

- ゆうちょダイレクト: 入出金明細CSV / 取扱内容照会(通帳未記入分)の保存HTML
- ゆうちょ紙通帳のOCR起こしCSV(手作業・過去分の一回きり)
- 三井住友銀行 入出金明細CSV
- 住信SBIネット銀行(NEOBANK)入出金明細CSV(sbi_hybrid 口座として取込)
- セゾン Netアンサー 月次請求CSV(請求メタで引落突合・鮮度判定)
- ビューカード(VIEW's NET)月次ご利用明細CSV(同上)
- PayPay 取引履歴CSV / PayPal 取引履歴CSV
- モバイルSuica SF利用履歴の保存HTML(Ctrl+S・SingleFile両対応)
- スターバックスカード利用履歴の保存HTML(SingleFile)
- Paidyご利用明細の保存HTML(SingleFile。残債を負債アンカーに計上)
- SBI証券(円貨入出金明細・ポートフォリオ・約定履歴・貴金属注文照会)
- 手入力残高CSV(`日付,口座,残高[,メモ]`。明細を取れない口座のアンカー。
  口座は accounts.toml のID、負債は未払額を負で記入)
- デモ給与明細CSV / デモDCポータルHTML(実在しない架空フォーマット。
  給与明細=総支給・控除を清算口座に計上、DC=評価額を残高アンカーに計上、
  という「勤務先系」ソースの実装例。デモデータ生成にも使う)

自分の口座のパーサは、リポジトリ本体を触らずに追加することもできる:
リポジトリ直下に `parsers_extra.py` を置き、`parsers.register()` で
sniff・パーサ・振り分け先を登録する(書き方は parsers.py 冒頭のコメント)。
テストは `tests_extra/` に置けば `discover tests` に合流する。
リポジトリに入れたくない口座(勤務先関連など)はこの拡張点に置くとよい。

## 明細の取込フロー

1. 情報鮮度モニタ(webUI)が古い口座を知らせる。各行の「手順」でその口座のダウンロード方法(accounts.toml の howto)を確認できる。
2. サイトからCSVをDL。CSVのないサイト(Suica/Paidy/スタバ等)はSingleFile拡張で表示中のページをHTML保存する。
3. serve.py で開いたwebUIなら、ヘッダの「⤓ 取込」かページへのドラッグ&ドロップだけでよい(inbox保存→自動振り分け→再ビルド→再読込まで一気に実行される)。
   手動なら data/inbox/ に置く(内容で自動判別するためリネーム不要)。ビルド時に raw/ の各ソースフォルダへ自動振り分け・改名される。
   内容に日付がないCSV(SBIポートフォリオ)は取得日プレフィックスが付く。
4. `python3 build.py` で再生成(重複期間があっても冪等)。webUIヘッダの「↻」でも再ビルドできる(serve.py 配信時のみ)。

## 仕組みの要点

- **冪等取込**: 同じファイルを2回置いても、期間の重なるファイルを追加しても
  増殖しない。ソース固有IDがあれば優先し、なければ
  (口座, 日付, 金額, 正規化摘要, 同日同額連番) で同定。
- **摘要の正規化**: 分離濁点の結合 + NFKC + 空白圧縮で、同一取引の
  媒体間表記ゆれ(半角カナ vs 全角)を吸収。
- **残高列の整合検証**: 残高列を持つ口座は「前日残高+当日の取引合計=
  当日のいずれかの残高」を日単位で検証し、OCR転記ミスや行の欠落を
  ビルド時に検出する(順序非依存)。
- **振替相殺**: rules.toml のパターンで内部移動(カード引落・チャージ等)を
  収支から除外。これを外すと支出が二重計上されるため最重要。両側にデータが
  ある振替は金額・日付窓でペアリングし、`require_pair = true` のルールは
  ペア成立時のみ振替(不成立は通常分類に降格)。`amount_min`/`amount_max`
  で金額条件も付けられる。
- **分類**: rules.toml の正規表現のみで機械的に付与。未分類は未分類のまま
  残し、推測で確定しない。チャートは `[category_groups]` の中分類で束ねる。
- **ポイント**: 機関の記録形態に従う。残高に入るもの(PayPayポイント)は
  収入、請求から引かれるもの(永久不滅の充当)は相殺、明細にも残高にも
  現れないもの(JRE POINT等)は存在しない扱い。ポイント残高は資産計上しない。
- **手動上書き**: serve.py で開いたときのみ、明細タブからカテゴリ(収支
  レコード)とコメント(全レコード)を編集できる。overrides.toml に保存され
  レコードIDで突合(突合できなくなると build が警告)。繰り返し未分類になる
  店はルール追加(rules.toml)の方が適切。
- **serve.py**: 標準ライブラリのみのサーバ(既定は 127.0.0.1 待受。外部公開は
  「サイト配信運用」の節を参照)。UIから書けるのは overrides.toml /
  uistate.toml / inbox への新規保存だけで、raw/ や rules.toml はサーバ経由でも
  書き換え不能。壊れたTOMLとクロスオリジンPOSTは拒否し、TOMLの書き換え時は
  直前版を `<name>.bak` に残す。
- **合算期間の宣言**: 紙通帳の「合算」行のように複数取引が1行に潰れた期間は
  引落の個別行が無くカード請求と突合できない。本物の取込漏れ警告を
  埋もれさせないよう、accounts.toml の `merged_periods` で宣言して
  検証対象外にする(何件を畳んだかはデータに無く自動判定できない)。
- **カード未払残の合成**: カードの明細には「利用」しか無く、そのままでは
  未払残が純資産に現れない。請求メタ(支払日・請求額)から**確定した請求
  だけ**を未払残として月末アンカーを置く。未請求の直近利用分は含まず、
  次の請求書を取り込むまで `次回請求待ち` と表示される。
- **残高アンカー合成**: 口座ごとの最新残高(明細の残高列・ポートフォリオ
  評価額・手入力)を時点バラバラのまま単純合算して資産総額とする。
  厳密さより「判明分の合成」を日付・鮮度表示とともに正直に見せる方針。
  明細から復元できない積み上がり(借入の実行等)は accounts.toml の accrual 宣言で
  月次アンカーを合成する。

## webUI

7タブ構成(概要・資産・給与・収支・年次・計画・明細)。タブは URL ハッシュ
(#summary 等)に対応し、ブラウザの戻る/進むで遡れる。

- **概要**: 1画面ダッシュボード(純資産・先月収支実績・当月暫定収支・
  貯蓄率・防衛資金・運用効率・資産構成・直近30日カテゴリ・引落予定)。
  当月暫定収支は「収入予定 − 固定費(宣言) − max(判明変動費, 平常ペース)」の
  着地見込みで、カード請求ラグ中も楽観に振れない。運用効率は利息・配当・
  評価損益(DC・証券)を平均総資産で割り、残高履歴のある全期間で
  年率換算した金額加重リターン。
- **資産**: 口座残高・資産構成・純資産推移(負債は下向きの赤、証券の含み益は
  斜線)・投資(保有・月次買付/売却・配当)。
- **給与**: 月収・年収換算(総支給/手取り)のサマリ、月例と賞与を分離した
  支給/控除の分解チャート・手取り率推移。給与明細の「勤務内容等」欄(勤怠・
  時間外・単価等)も余さず転記し、推移チャートと全項目表で見せる。
- **収支**: 月内資金推移の重ね描き(各月を月初=0で重ね、薄い帯=過去月の
  25〜75%レンジで当月のペースを比べる)・月次収支・支出の内訳ドリルダウン・
  カテゴリ推移・貯蓄率・日別支出ヒートマップ・資金の流れ(口座間ネットワーク
  /収支サンキー)・定期支出(自動検出)。
- **年次**: 年ごとの収支・貯蓄率・年末純資産・法定控除の表と、支出の中分類
  積み上げ。確定申告・年末の振り返り用。
- **計画**: 資金繰り予測(定期支出・給与・確定カード請求・検出した定期振替を
  引落日に投影し、日を打てない残りの流出は実績中央値で概算して3ヶ月投影)・
  予定入出金の表・純資産の長期投影(貯蓄・投資率スライダー付き)。
- **明細**: 検索・フィルタ・絞り込み結果のCSVダウンロード。行クリックで
  分類根拠(どのルールがなぜ適用され、振替候補がどう降格したか)・原文を
  展開表示。未分類の多い摘要を件数順に一覧し、ルールを書く優先順位を
  決められる(`build.py --check` も同じ集計を出す)。

主要な導線・機能:

- 支出のドリルダウンは 中分類→カテゴリ→摘要→明細 と掘れて、明細タブの
  該当レコードにジャンプしてハイライトする。月次系チャートの棒/線クリックで
  その月の収支モーダルが開く。
- グローバルトグル(localStorage永続): 収入=総支給/手取り(手取りは法定控除
  のみ差引き)、振替・調整を明細表から隠す。
- 情報鮮度モニタ: 口座ごとの取込の新しさを監視。意味の違う日付を列で分けて
  表示する — 「明細末端」=レコードの取引日末端、「取込」=DL・保存の実日付、
  「〜YYYY-MM請求 / 〜YYYY-MM支給」=カバー宣言(レコード日が構造的に遅れる
  カード・給与の鮮度はこれで測る)、「次回」=放置すると警告が出る日。
  「更新確認」で警告を期待間隔ぶん止め、「通知オフ」で監視から外せる
  (状態は data/uistate.toml、`build.py --check` も尊重)。

## サイト配信運用(Ubuntu server)

serve.py は TLS を持たない。中身は全明細なので、公開時の構成は
**「serve.py は 127.0.0.1 のまま + Basic認証、HTTPS はプロキシで終端」**
に固定する。

- **非ローカルのアクセスは Basic認証が必須**(クライアント単位で判定)。
  接続元がループバックでないリクエストと、リバースプロキシ・トンネル経由を
  示す転送ヘッダ(X-Forwarded-For 等)付きのリクエストが非ローカル扱いで、
  認証は環境変数 `KAKEIBO_AUTH=user:pass`(または `--auth`)で設定する。
  未設定のまま非ローカルから届いたアクセスは 403 で拒否(fail-closed)。
  同一マシンからの直接アクセスは認証なしで従来どおり使える。
  ループバック以外での待受(`--host 0.0.0.0`)は認証なしだと起動自体を拒否。
- プロキシは X-Forwarded-For を付けること(Caddy・nginx・tailscale serve は
  既定で付く。外すと serve.py が非ローカルと判定できず認証を課せない)。

serve.py の常駐(systemd):

```ini
# /etc/systemd/system/kakeibo-p.service
[Unit]
Description=kakeibo-p web UI
After=network.target

[Service]
User=youruser
WorkingDirectory=/home/youruser/kakeibo-p
# /etc/kakeibo-p.env には KAKEIBO_AUTH=user:pass を書き chmod 600 にする
EnvironmentFile=/etc/kakeibo-p.env
# python3バイナリの指定は適宜に
ExecStart=/home/youruser/miniconda3/bin/python3 serve.py
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

`sudo systemctl enable --now kakeibo-p` で起動。

**Tailscaleでのページ配信**
自分の端末からしか見ないなら公開する必要自体がない。サーバと手元の端末に
Tailscale を入れ、

```sh
tailscale serve --bg http://localhost:8765
```

で tailnet 内限定の HTTPS URL が生える(証明書も自動)。ポート開放もドメイン取得も不要。
tailscale serve 経由も転送ヘッダで非ローカル扱いになるので、KAKEIBO_AUTH の設定は必要。
