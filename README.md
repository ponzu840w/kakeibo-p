# kakeibo-p

個人の全金融口座について、残高(ストック)と取引(フロー)をまとめて把握する
ファイルベースの家計管理システム。DBMSは使わず、webUIは基本的に静的HTML。

めちゃくちゃclaude製。

## 設計原則

1. **raw/ は不変の一次資料**。ダウンロードした明細CSVなどの原本は改変しない。ただし、ファイル名が一意にならないものは最初に一度だけ改名することがある。
2. **raw/ 以外はすべて派生物**。`ledger/` も `site/data.js` も、`build.py` を再実行すれば raw/ から再生成できる。パーサを直したら全履歴を作り直せるように設計する。
3. **決定論的な処理と、非決定論的な分析をはっきり分ける**。取込・正規化・分類・集計は決定論的なコードだけで行い、確定データへの書き込み経路にAI・LLMを置かない。AIは読み取り専用の分析相談役に限る。
4. **DBMSは使わない**。ソース・オブ・トゥルースはテキストファイル(JSONL/TOML/CSV)。
5. **webUIは静的構成を基本とする**。`site/index.html` をダブルクリックすれば開ける。file:// ではCORS制限でfetchが失敗するため、データは `data.js` に埋め込む。外部CDNには依存せず、チャートは素のSVGで描く。

## リポジトリ構成

```
kakeibo-p/                # gitリポジトリ(コードのみ)
├── build.py              # パイプライン本体(重複排除・分類・突合・集計・出力)
├── parsers.py            # ソース別パーサと形式判別(新ソース追加はここだけ)
├── model.py              # 基本部品(正規化・Txn型・パス定数)
├── serve.py              # UIのローカル配信と上書き保存API(任意。file://でも動く)
├── site/                 # 静的UI(index.html / style.css / js/ に機能別に分割)
│   ├── data.js           # 集計用データ(派生物・git外・ローカル)
│   └── data.demo.js      # デモ用データ(実データがないときに読まれる)
├── tests/                # テスト(架空データ。JS側の計算ロジックも含む)
├── demo/build_demo.py    # 架空データの生成とデモビルド
├── parsers_extra.py      # ローカル拡張パーサ(任意。勤務先関連などを分離)
├── tests_extra/          # ローカル拡張のテスト(任意。discoverに合流)
├── ledger/YYYY-MM.jsonl  # 正規化済みトランザクション(派生物・git外・ローカル)
├── CLAUDE.md → data/CLAUDE.md   # リンク(git外)
└── data/                 # 個人データの実体。git外
    ├── raw/<source>/     #   明細の原本(不変。配置・命名は自由)
    ├── inbox/            #   取込ファイルの置き場(build が raw/ へ振り分ける)
    ├── accounts.toml     #   口座台帳(取得手順メモの howto を含む)
    ├── rules.toml        #   分類ルール(正規表現→カテゴリ)・振替定義・中分類
    ├── overrides.toml    #   レコード単位の手動上書き(UI生成物)
    ├── uistate.toml      #   鮮度モニタの状態(UI生成物)
    └── build_log.jsonl   #   ビルド実行の追記専用ログ(build.py が書く。
                          #    再生成できない履歴なので、派生物ではなく
                          #    状態ファイルとして扱う。直近分はUIヘッダの
                          #    「ログ」から見られる)
```

**個人データはgitに入れない。** `data/` の実体はクラウドストレージ(OneDrive等)に
置き、シンボリックリンクで参照すれば build.py はそのまま動く。派生物(ledger/ と
site/data.js)は再生成できるので、ローカルに置くだけでよい。

## 使い方

```sh
python3 build.py          # 全再生成(ledger/ と site/data.js を書き直す)
python3 build.py --check  # 生成せず、取込サマリ・検証結果・鮮度警告だけを表示
python3 serve.py          # UIをローカル配信(明細の上書き編集はこの経路でだけできる)
python3 serve.py --demo   # 架空データで配信(data/ が無くても動く。再ビルドもできる)
python3 -m unittest discover tests   # テスト
python3 demo/build_demo.py           # 架空データを生成してデモビルド
```

Python 3.11以上で、標準ライブラリだけで動く。

動きを見たいだけなら、`site/index.html` を開けばよい。同梱の
`site/data.demo.js`(`demo/build_demo.py` で作り直せる)が読み込まれ、固定シードで
生成した架空の家計2年分でダッシュボード一式が動く。実データ(`site/data.js`)を
ビルドすると、そちらが優先される。

`python3 serve.py --demo` で起動すると読み書きの対象がすべて `demo/` になるので、
上書き編集・取込・再ビルド(↻)まで架空データで試せる。`data/`(個人データ)が
ない状態で `build.py` や `serve.py` をそのまま実行すると、エラーで止まる。

## 実装済みパーサ

ソースはファイル名ではなく内容(ヘッダ)で自動判別する。ソース固有の仕様や罠は
parsers.py の各パーサの docstring にある。

- ゆうちょダイレクト: 入出金明細CSV / 取扱内容照会(通帳未記入分)の保存HTML
- ゆうちょ紙通帳のOCR起こしCSV(手作業・過去分の一回きり)
- 三井住友銀行 入出金明細CSV
- 住信SBIネット銀行(NEOBANK)入出金明細CSV(ハイブリッド預金の連携解除までは
  sbi_hybrid 口座、解除後は代表口座 sbinet として取込)
- SBI新生銀行 入出金明細CSV(SBIハイパー預金。sbi_shinsei 口座として取込)
- セゾン Netアンサー 月次請求CSV(請求メタで引落突合・鮮度判定)
- ビューカード(VIEW's NET)月次ご利用明細CSV(同上)
- PayPay 取引履歴CSV / PayPal 取引履歴CSV
- モバイルSuica SF利用履歴の保存HTML(Ctrl+S・SingleFile両対応)
- スターバックスカード利用履歴の保存HTML(SingleFile)
- Paidyご利用明細の保存HTML(SingleFile。残債を負債アンカーに計上)
- SBI証券(円貨入出金明細・ポートフォリオ・約定履歴・貴金属注文照会・
  金・銀・プラチナ取引の月次/年次報告書PDF)
- SBI証券 My資産の資産推移CSV(ポートフォリオを保存し始める前の評価額を補う)
- 手入力残高CSV(`日付,口座,残高[,メモ]`。明細を取れない口座のアンカー。
  口座は accounts.toml のID、負債は未払額を負で記入)
- デモ給与明細CSV / デモDCポータルHTML(実在しない架空フォーマット。
  「勤務先系」ソースの実装例で、給与明細は総支給・控除を清算口座に、DCは
  評価額を残高アンカーに計上する。デモデータの生成にも使う)

自分の口座のパーサは、リポジトリ本体を触らずに追加することもできる。
リポジトリ直下に `parsers_extra.py` を置き、`parsers.register()` で
sniff・パーサ・振り分け先を登録する(書き方は parsers.py 冒頭の docstring)。
テストは `tests_extra/` に置けば `discover tests` に合流する。
リポジトリに入れたくない口座(勤務先関連など)は、この拡張点に置くとよい。

## 明細の取込フロー

1. 情報鮮度モニタ(webUI)が、取込の古くなった口座を知らせる。各行の「手順」で、その口座のダウンロード方法(accounts.toml の howto)を確認できる。
2. 各サイトからCSVをダウンロードする。CSVを出せないサイト(Suica/Paidy/スタバ等)は、表示中のページをSingleFile拡張でHTMLとして保存する。
3. serve.py で開いたwebUIなら、ヘッダの「⤓ 取込」を押すか、ページにファイルをドラッグ&ドロップするだけでよい。inboxへの保存、raw/ への振り分け、再ビルド、再読込までを続けて実行する。
   手動で取り込むときは data/inbox/ に置く。ソースは内容で判別するので改名はいらない。ビルド時に raw/ の各ソースフォルダへ振り分けられ、改名される。
   内容に日付がないCSV(SBIポートフォリオ)には、ファイル名に取得日のプレフィックスが付く。
4. `python3 build.py` で再生成する。期間が重なるファイルがあっても結果は変わらない(冪等)。serve.py で配信しているときは、webUIヘッダの「↻」でも再ビルドできる。

## 仕組みの要点

- **冪等取込**: 同じファイルを2回置いても、期間の重なるファイルを追加しても、
  取引は重複しない。取引の同定には、ソース固有のIDがあればそれを使い、なければ
  (口座, 日付, 金額, 正規化摘要, 同日同額連番)の組を使う。
- **摘要の正規化**: 分離した濁点の結合、NFKC、空白の圧縮によって、同じ取引の
  媒体による表記ゆれ(半角カナと全角など)を吸収する。
- **残高列の整合検証**: 残高列を持つ口座では、「前日残高+当日の取引合計=
  当日のいずれかの残高」が成り立つかを日単位で検証する。行の順序には依存しない。
  これでOCRの転記ミスや行の欠落をビルド時に検出する。
- **振替相殺**: rules.toml のパターンで内部移動(カード引落・チャージ等)を
  収支から除く。この相殺がないと支出が二重計上されるので、最も重要な仕組み。
  両側の口座に明細がある振替は、金額と日付の窓でペアを組む。
  `require_pair = true` のルールはペアが成立したときだけ振替とし、成立しなければ
  通常の分類に降格する。`amount_min`/`amount_max` で金額の条件も付けられる。
- **分類**: カテゴリは rules.toml の正規表現だけで機械的に付ける。ルールに
  当たらない取引は未分類のまま残し、推測でカテゴリを確定しない。チャートでは
  `[category_groups]` の中分類でまとめる。
- **ポイント**: 扱いは機関の記録のしかたに従う。残高に入るもの(PayPayポイント)は
  収入、請求から引かれるもの(永久不滅の充当)は相殺とし、明細にも残高にも
  現れないもの(JRE POINT等)はないものとして扱う。ポイント残高は資産に計上しない。
- **手動上書き**: serve.py で開いたときだけ、明細タブからカテゴリ(収支レコード)と
  コメント(全レコード)を編集できる。編集内容は overrides.toml に保存され、
  レコードIDで明細と突き合わせる。突き合わせられなくなると build が警告する。
  何度も未分類になる店には、上書きよりも rules.toml にルールを足すほうが適切。
- **serve.py**: 標準ライブラリだけで書いたサーバで、既定では 127.0.0.1 で
  待ち受ける(外部公開は「サイト配信運用」の節を参照)。UIから書き込めるのは
  overrides.toml と uistate.toml と、inbox への新規保存だけ。raw/ や rules.toml は
  サーバ経由でも書き換えられない。パースできないTOMLとクロスオリジンのPOSTは
  拒否し、TOMLを書き換えるときは直前の版を `<name>.bak` に残す。
- **合算期間の宣言**: 紙通帳の「合算」行のように複数の取引が1行にまとめられた
  期間は、引落の個別行がないのでカード請求と突き合わせられない。本当の取込漏れの
  警告がこれに埋もれないよう、そうした期間は accounts.toml の `merged_periods` で
  宣言して検証から外す。何件の取引が1行にまとめられたかはデータにないので、
  自動では判定できない。
- **カード未払残の合成**: カードの明細には利用の行しかなく、そのままでは
  未払残が純資産に現れない。そこで請求メタ(支払日・請求額)から、**確定した
  請求だけ**を未払残とする月末アンカーを置く。まだ請求されていない直近の利用分は
  含めず、次の請求書を取り込むまで `次回請求待ち` と表示する。
- **残高アンカー合成**: 口座ごとの最新残高(明細の残高列・ポートフォリオ
  評価額・手入力)を、時点がそろっていないまま単純に足して資産総額とする。
  厳密さよりも、判明している分の合計を日付と鮮度の表示とともに正直に見せる方針。
  明細から復元できない負債の積み上がり(借入の実行等)は、accounts.toml の
  accrual 宣言から月次アンカーを合成する。

## webUI

タブは7つ(概要・資産・給与・収支・年次・計画・明細)。各タブはURLハッシュ
(#summary等)と対応しているので、ブラウザの戻る/進むでタブを行き来できる。

- **概要**: 1画面のダッシュボード(純資産・先々月収支実績・当月暫定収支・
  貯蓄率・防衛資金・運用効率・資産構成・直近30日カテゴリ・引落予定)。
  当月暫定収支は「収入予定 − 固定費(宣言) − max(判明変動費, 平常ペース)」で
  出す着地見込みで、カード請求が明細に現れるまでの間も楽観側にずれない。
  運用効率は、利息・配当・評価損益(DC・証券)を平均総資産で割り、残高履歴の
  ある全期間で年率換算した金額加重リターン。
- **資産**: 口座残高・資産構成・純資産推移(負債は下向きの赤、証券の含み益は
  斜線)・投資(保有・月次買付/売却・配当)。
- **給与**: 月収・年収換算(総支給/手取り)のサマリ、月例と賞与を分けた
  支給/控除の分解チャート、手取り率推移。給与明細の「勤務内容等」欄(勤怠・
  時間外・単価等)も残らず転記し、推移チャートと全項目表で見せる。
- **収支**: 月内資金推移の重ね描き(各月の月初を0として重ね、過去月の25〜75%の
  範囲を薄い帯で示して当月のペースと比べる)・月次収支・支出の内訳ドリルダウン・
  カテゴリ推移・貯蓄率・日別支出ヒートマップ・資金の流れ(口座間ネットワーク
  /収支サンキー)・定期支出(自動検出)。
- **年次**: 年ごとの収支・貯蓄率・年末純資産・法定控除の表と、支出の中分類
  積み上げ。確定申告や年末の振り返りに使う。
- **計画**: 資金繰り予測・予定入出金の表・純資産の長期投影(貯蓄・投資率
  スライダー付き)。資金繰り予測は、定期支出・給与・確定したカード請求・検出した
  定期振替を引落日に置き、日付を決められない残りの流出は実績の中央値で概算して、
  3ヶ月先まで投影する。
- **明細**: 検索・フィルタ・絞り込み結果のCSVダウンロード。行をクリックすると、
  分類根拠(どのルールがなぜ適用され、振替候補がどう降格したか)と原文を
  展開する。未分類の多い摘要を件数順に一覧し、どのルールから書くかを
  決められる(`build.py --check` も同じ集計を出す)。

### 主要な導線・機能

- 支出のドリルダウンは 中分類→カテゴリ→摘要→明細 と掘り下げられ、最後は
  明細タブの該当レコードにジャンプしてハイライトする。月次系チャートの棒や線を
  クリックすると、その月の収支モーダルが開く。
- グローバルトグル(localStorageに保存): 収入を総支給/手取りで切り替える
  (手取りは法定控除だけを差し引く)。振替・調整を明細表から隠す。
- 情報鮮度モニタ: 口座ごとに取込の新しさを監視する。意味の違う日付は列を
  分けて表示する。「明細末端」はレコードの取引日の末端、「取込」はDL・保存の
  実日付、「経過」は警告の判定に使う経過日数、「次回目安」は放置すると警告が
  出る日。カードと給与はレコード日が構造的に遅れるので、「〜YYYY-MM請求 /
  〜YYYY-MM支給」のカバー宣言で鮮度を測り、「取込」の列に表示する。
  「更新確認」を押すと警告を期待間隔の分だけ止め、「通知オフ」で監視から外せる
  (状態は data/uistate.toml に保存され、`build.py --check` も参照する)。

## サイト配信運用(Ubuntu server)

serve.py はTLSに対応していない。配信する中身は全明細なので、公開するときの構成は
**「serve.py は 127.0.0.1 で待ち受けたままBasic認証をかけ、HTTPSはプロキシで
終端する」** に固定する。

- **非ローカルからのアクセスにはBasic認証が必須**(クライアント単位で判定)。
  非ローカルとみなすのは、接続元がループバックでないリクエストと、
  リバースプロキシやトンネルの経由を示す転送ヘッダ(X-Forwarded-For等)が
  付いたリクエスト。認証情報は環境変数 `KAKEIBO_AUTH=user:pass`(または
  `--auth`)で設定する。設定しないまま非ローカルからアクセスが届くと、403で
  拒否する(fail-closed)。同じマシンからの直接アクセスは認証なしで使える。
- ループバック以外で待ち受ける指定(`--host 0.0.0.0`)は、認証を設定して
  いなければ起動自体を拒否する。
- プロキシはX-Forwarded-Forを付けること。外すと serve.py が非ローカルからの
  アクセスだと判定できず、認証をかけられない。同じホストのプロキシからの接続は
  127.0.0.1 から届くので、全明細が認証なしで外に出る。Caddy と tailscale serve は
  既定で付ける。nginx は既定では付けないので、
  `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` を明示する。

### serve.py の常駐(systemd)

```ini
# /etc/systemd/system/kakeibo-p.service
[Unit]
Description=kakeibo-p web UI
After=network.target

[Service]
User=youruser
WorkingDirectory=/home/youruser/kakeibo-p
# /etc/kakeibo-p.env には KAKEIBO_AUTH=user:pass を書き chmod 600 にする
EnvironmentFile=/etc/kakeibo-p.env
# python3 のパスは環境に合わせる
ExecStart=/usr/bin/python3 serve.py
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

`sudo systemctl enable --now kakeibo-p` で起動する。

### Tailscaleでのページ配信

自分の端末からしか見ないなら、そもそも公開する必要がない。サーバと手元の端末に
Tailscaleを入れ、サーバで次を実行すると、tailnet内だけで開けるHTTPSのURLで
配信される。証明書も自動で用意され、ポート開放もドメイン取得もいらない。

```sh
tailscale serve --bg http://localhost:8765
```

tailscale serve 経由のアクセスも転送ヘッダによって非ローカル扱いになるので、
KAKEIBO_AUTH の設定は必要。
